# 招募问卷后端实施方案

## 1. 目标与边界

本周目标是让第二阶段招募问卷成为可对外发放的真实闭环：

```text
专属邀请链接 → 问卷填写 → 手机号验证 → 保存结果
→ 邀请关系和体验时长入账 → 结果页可找回
```

本周只实现问卷阶段。用户看到的是“邀请链接”，不是邀请码；只要受邀人完成本轮问卷提交，邀请人即获得 1 小时体验时长。是否为已有游戏账号不影响本轮奖励资格。

问卷和游戏保持独立登录态。问卷后端只在每次“提交”或“查看结果”时验证手机号，不向浏览器下发或长期保存游戏登录令牌。

以下内容不在本周实现：游戏内个人邀请码、进入体验判定、游戏内资源展示和游戏账号登录页改造。

## 2. 本周数据模型

所有表均以 `customer_code` 作为与游戏账号关联的稳定身份，不用手机号作为关系主键。手机号只在验证环节使用；日志中必须脱敏，答案中的历史手机号按现有隐私规范存储和访问。

### 2.1 `recruitment_application`

一位用户在一次招募活动中只有一条有效问卷。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `campaign_code` | 本轮招募活动标识，例如 `phase2_recruitment` |
| `customer_code` | 已验证游戏账号标识 |
| `status` | `success`（已提交）或 `granted`（名额已发放） |
| `answers_json` | 全量问卷答案，不含短信验证码和登录令牌 |
| `submitted_at` | 首次提交时间 |
| `created_at` / `updated_at` | 审计字段 |

约束：`UNIQUE(campaign_code, customer_code)`。

### 2.2 `recruitment_referral_link`

问卷阶段的专属邀请链接。`referral_token` 是不可读的随机字符串，不编码用户 ID、手机号或邀请码。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `campaign_code` | 招募活动标识 |
| `owner_customer_code` | 分享链接的归属用户 |
| `referral_token` | URL 安全的随机标识，建议至少 128 位随机熵 |
| `status` | `active`、`inactive` 或 `expired` |
| `expire_at` | 可为空；本轮结束时统一失效 |
| `created_at` / `disabled_at` | 审计字段 |

约束：`UNIQUE(referral_token)`、`UNIQUE(campaign_code, owner_customer_code)`。

### 2.3 `recruitment_referral_conversion`

记录一次“受邀人完成问卷提交”的成功事件。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `campaign_code` | 招募活动标识 |
| `link_id` | 使用的邀请链接 |
| `inviter_customer_code` | 邀请人 |
| `invitee_customer_code` | 受邀人 |
| `event_type` | 固定为 `questionnaire_submitted` |
| `converted_at` | 成功提交时间 |

约束：`UNIQUE(campaign_code, invitee_customer_code)`，确保一位受邀人本轮最多给一位邀请人计奖。

### 2.4 `recruitment_reward_ledger`

资源发放流水。不要只维护结果页上的汇总数，必须保留可追溯的逐笔记录。

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `customer_code` | 资源归属用户，即邀请人 |
| `campaign_code` | 招募活动标识 |
| `resource_type` | 本周固定为 `experience_hours` |
| `amount` | 本周每次有效邀请固定为 `1` |
| `source_conversion_id` | 对应邀请成功记录 |
| `created_at` | 发放时间 |

约束：`UNIQUE(source_conversion_id)`，确保重试或并发请求不会重复发放时长。

## 3. 前后端接口

前端已经按以下接口实现，服务地址由 `VITE_RECRUITMENT_API_BASE_URL` 提供。例如服务地址为 `https://recruitment.example.com` 时，前端会请求其下的 `/api/recruitment/...` 路径。

统一成功外层：

```json
{ "code": 200, "message": "ok", "data": {} }
```

业务错误使用非 `200` 的 `code` 和可向用户展示的 `message`。不得在错误文案中暴露他人的手机号、账号状态或邀请人身份。

### 3.1 发送短信验证码

`POST /api/recruitment/sms-code`

```json
{ "mobileNum": "用户输入的手机号" }
```

后端职责：校验手机号格式、限流，然后服务端调用现有短信验证码能力。前端不会直接调用游戏账号接口。

### 3.2 提交问卷

`POST /api/recruitment/applications`

```json
{
  "mobileNum": "用户输入的手机号",
  "smsCode": "六位短信验证码",
  "answers": {
    "identity": "否"
  },
  "referralToken": "可为空的邀请链接归因标识"
}
```

`answers` 是全部问卷字段，不包含 `mobileNum`、`smsCode` 或任何令牌。`referralToken` 缺失或无效时，仍正常提交问卷，只是不产生邀请归因。

后端先完成手机号验证；随后在一次数据库事务中完成问卷、邀请关系和资源流水写入：

1. 调用既有手机号登录/验证能力，确认验证码有效并取得 `customer_code`；若登录返回没有该字段，则在服务端使用登录结果查询账号资料后取得它。
2. 查找或创建该用户本轮的 `recruitment_application`；重复提交返回既有结果，不重复计奖。
3. 为提交者查找或创建一条 `active` 的问卷邀请链接。
4. 若请求带有效 `referralToken`，且链接仍有效、链接归属者不是本人、受邀人尚未被归因，则写入 `recruitment_referral_conversion`。
5. 为邀请人写入一条 1 小时 `recruitment_reward_ledger`；由唯一约束防止重复发放。
6. 返回当前提交者的结果页数据。

### 3.3 验证手机号并找回结果

`POST /api/recruitment/result-session`

```json
{
  "mobileNum": "提交时使用的手机号",
  "smsCode": "六位短信验证码"
}
```

后端再次验证手机号后，按 `customer_code + campaign_code` 查找问卷。无记录时返回“未找到已提交问卷，请先填写问卷”；有记录时返回与提交接口相同的结果数据。这个接口不创建游戏登录会话，也不影响游戏的登录或退出状态。

### 3.4 结果数据

提交和找回接口的 `data` 字段固定为：

```json
{
  "phoneTail": "0000",
  "status": "success",
  "referralLink": "https://问卷域名/?ref=随机归因标识",
  "referralRecords": [{ "name": "已脱敏显示名" }],
  "successfulInvites": 2,
  "earnedHours": 2
}
```

- `phoneTail` 只返回手机号后四位。
- `status` 只允许 `success` 或 `granted`。
- `referralRecords` 最多返回 10 条，按成功时间倒序，`name` 必须脱敏。
- `successfulInvites` 和 `earnedHours` 返回全量累计数，不能因为列表只展示 10 条而截断。
- `referralLink` 是当前用户的问卷专属链接；`granted` 状态仍可返回该字段供后台保留，但前端不再展示“复制邀请链接”按钮。

## 4. 关键流程

### 4.1 普通提交

```text
填写问卷 → 获取短信 → 提交
→ 后端验证手机号并关联账号
→ 保存问卷 → 生成/读取个人邀请链接
→ 返回“提交成功”结果页
```

### 4.2 受邀提交与奖励

```text
邀请人复制专属链接
→ 受邀人以 ?ref=token 打开问卷
→ 前端保留 token 并在提交时传给后端
→ 后端确认受邀人完成本轮问卷
→ 写邀请成功记录和 1 小时资源流水
→ 邀请人下次查看结果页时看到累计变化
```

前端只负责携带 `referralToken`。邀请关系、是否自邀、重复提交、重复奖励和资源汇总均由后端判定。

### 4.3 已提交用户找回

```text
点击“已提交，验证手机号查看结果”
→ 输入提交手机号和短信验证码
→ 后端验证并返回结果
→ 前端恢复对应结果页
```

清除浏览器缓存或从新设备进入时，仍可通过该流程恢复，不依赖本地存储。

### 4.4 名额发放

运营将 `recruitment_application.status` 更新为 `granted` 后，用户再次查看结果页即显示“名额已发放”。问卷邀请记录可继续展示，但复制问卷邀请链接入口隐藏；体验邀请码海报与进入游戏的动作沿用前端已确认的页面，不在本周接游戏端逻辑。

## 5. 安全、幂等与隐私

- 短信发送必须按手机号、IP 和设备做限流；验证码校验、问卷保存和邀请计奖只能在 HTTPS 请求体中传递。
- 不在 URL、分享文案、浏览器存储或日志中写入验证码、游戏令牌或完整手机号。
- `referral_token` 使用安全随机数生成；不能由 `customer_code`、手机号或递增 ID 推导。
- 以数据库唯一约束而非内存判断保证：一位受邀人仅归因一次、一次归因仅发一笔奖励。
- 如果同一用户使用自己的链接提交问卷，问卷可正常提交，但不得创建邀请成功记录或资源流水。
- 问卷提交接口应允许网络重试，始终返回同一份结果，不因重试重复增加时长。
- 只允许问卷前端域名跨域访问；若无法配置跨域，则由同域反向代理转发招募接口。

## 6. 本周联调与上线验收

后端完成后，用两个测试手机号验证以下场景：

1. 无邀请链接的用户完成提交，得到自己的结果页和专属邀请链接。
2. 第二个手机号通过该链接完成提交，邀请人结果页增加 1 位成功记录和 1 小时时长。
3. 第二个手机号重复提交，不增加第二条邀请记录，也不重复发放时长。
4. 邀请人使用自己的链接提交，不给自己发放时长。
5. 清除浏览器数据后，两个手机号都能通过短信验证码找回各自结果。
6. 运营将一位用户切到 `granted` 后，该用户结果页显示名额发放状态，不再显示复制问卷邀请链接按钮。
7. 后端接口不可用、验证码错误、无已提交记录时，前端展示明确错误，不丢失已填写的问卷内容。

发布条件：以上场景通过，并在前端构建环境配置真实 `VITE_RECRUITMENT_API_BASE_URL`。未配置时是浏览器演示模式，不能用于公开收集数据。

## 7. 下周：游戏体验期的邀请码机制（仅结构复用）

下周不另起一套邀请数据。复用本周的“邀请标识、邀请成功事件、资源流水”骨架，并新增游戏阶段：

| 本周问卷阶段 | 下周游戏体验阶段 |
|---|---|
| 用户看到专属邀请链接 | 用户看到可复制、可手输的邀请码，以及携码游戏链接 |
| 成功事件是 `questionnaire_submitted` | 成功事件改为“使用码并实际进入体验” |
| 链接标识是不可读归因 token | 邀请码是用户可见的码，仍须由后端映射到归属用户 |
| 问卷提交后发放时长 | 进入体验后发放游戏阶段资源 |

届时在活动/邀请记录中增加阶段或事件类型即可；同一用户只允许一个阶段处于计奖状态。用户进入游戏体验阶段后，其问卷邀请链接停止计奖，游戏邀请码启用。具体游戏接口、邀请码格式和进入体验判定在下周另行设计，不阻塞本周上线。
