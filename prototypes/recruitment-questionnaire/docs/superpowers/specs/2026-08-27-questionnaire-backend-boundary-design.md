# 问卷正式数据接入设计

**目标：** 保持已确认的问卷视觉与流程不变，使前端可在招募后端完成后直接切换到真实手机号验证、提交、结果恢复和邀请归因。

**范围：** 本轮只改问卷前端与接口契约；不改 Unity WebGL、既有游戏账号服务和招募后端数据库。

## 已确认的产品规则

- 问卷与游戏保持独立登录态；问卷验证手机号只用于招募资源归属。
- 问卷阶段使用“专属邀请链接”，不向用户展示“邀请码”概念。
- 受邀人完成本轮问卷提交即为邀请成功，不区分是否为已有游戏账号。
- 游戏阶段的个人邀请码、进入体验判定和奖励发放不在本轮实现。
- 同一用户进入游戏体验阶段后，问卷邀请链接停止计奖。

## 前端链接规则

- 分享链接格式为 `https://问卷域名/?ref=<referralToken>`。
- `referralToken` 是后端生成、不可读的随机归因标识；前端不根据它推断邀请人身份。
- 前端只接受 URL 安全字符组成、长度在 6 至 96 之间的标识；无效标识按无邀请来源处理。
- 前端在打开问卷时读取 `ref`，并在提交时原样提交给招募后端。最终归因、反作弊和奖励判断全部由后端完成。

## 前后端接口契约

问卷前端只连接招募服务，不直接保存游戏登录令牌。招募服务在服务端调用既有手机号短信登录能力，完成校验和账号关联。

### `POST /api/recruitment/sms-code`

请求：

```json
{ "mobileNum": "13800000000" }
```

成功响应：

```json
{ "code": 200, "message": "验证码已发送" }
```

### `POST /api/recruitment/applications`

请求：

```json
{
  "mobileNum": "13800000000",
  "smsCode": "123456",
  "answers": { "identity": "否" },
  "referralToken": "7xKp9mQ2"
}
```

`answers` 保存问卷中的全部填写字段，不包含手机号和验证码。`referralToken` 可为 `null`。后端以一次事务完成：短信校验、问卷幂等保存、邀请关系归因、奖励流水与结果返回。

成功响应的 `data`：

```json
{
  "phoneTail": "0000",
  "status": "success",
  "referralLink": "https://问卷域名/?ref=7xKp9mQ2",
  "referralRecords": [{ "name": "回响玩家 A**" }],
  "successfulInvites": 1,
  "earnedHours": 1
}
```

### `POST /api/recruitment/result-session`

请求：

```json
{ "mobileNum": "13800000000", "smsCode": "123456" }
```

成功响应的 `data` 与提交接口一致。未提交时返回可展示的业务错误；不得泄露其他手机号或邀请人信息。

## 前端运行模式

- 不设置 `VITE_RECRUITMENT_API_BASE_URL` 时保留原型演示模式，仅能用于内部体验。
- 设置该变量后，前端将请求 `${VITE_RECRUITMENT_API_BASE_URL}/api/recruitment/...`，不再把问卷数据作为正式记录写入浏览器存储。
- 对外发放前必须配置真实招募服务；演示模式不能作为正式发布方案。

## 验收标准

1. 带 `ref` 链接进入的受邀人提交时，前端请求体包含该标识。
2. 无效或缺失 `ref` 不阻止用户正常提交。
3. 前端可通过一个环境变量切换演示与真实接口，不改页面文案或问卷字段。
4. 提交成功和“验证手机号查看结果”均使用后端返回的邀请记录、奖励和分享链接。
5. 现有四步问卷、两种结果页和游戏模拟页回归通过。
